# Arsenal — 데이터 엔지니어링 문제 해결 도구 체계

> 데이터 엔지니어링에서 반복적으로 사람을 괴롭히는 문제들을, 로마 무기 체계에 대응시켜 하나씩 도구화한다.

## 포지셔닝 — 무엇을 만들려는가

Databricks·Snowflake 수준의 **완성도**를 가진 솔루션을, 그들과 정반대의 **형태**로 만든다.

- **그들**: 모든 것을 떠안는 하나의 거대한 플랫폼. 강력하지만 무겁고, 한번 들어가면 나오기 어렵다(락인). 작게 시작하기 어렵고, 한 문제만 풀려 해도 전체를 사야 한다.
- **우리**: 데이터 엔지니어가 겪는 **각각의 문제**에 대해, 작고 날카로운 도구가 **가장 우아한 해결책 하나**를 보여준다. 도구 하나하나의 완성도는 그들 수준을 노린다.

핵심 약속은 "한 문제, 최고의 해결책"이다. 큰 플랫폼이 백 가지를 80점으로 하는 동안, 우리는 한 가지를 100점으로 한다 — 그런 도구를 여러 개.

### 제품군의 관계 — 독립하되 시너지 (Unix 철학)

각 도구는 **독립 제품**이다. 따로 도입할 수 있고, 다른 도구 없이도 제값을 한다. 동시에 작은 공통 인터페이스(Arrow/Parquet 허브, 공유 상태 규약)로 **느슨하게 맞물려**, 같이 쓰면 시너지가 난다.

- 한 가지를 잘한다 (do one thing well)
- 작고 표준적인 인터페이스로 연결된다 (느슨한 결합)
- 어떤 도구든 빼거나 다른 것으로 갈아끼울 수 있다 (락인 없음)

이것이 "거대 플랫폼 락인" 대비 우리의 구조적 차별점이다.

## 제품 철학 (모든 판단의 기준)

네 가지를 동시에 만족시킨다. 하나를 위해 나머지를 희생하지 않는다. 기능을 더할 때마다 "이게 넷을 다 지키나?"를 되묻는다.

- **가볍게** — 작게 시작한다. 한 도구만 집어 바로 쓸 수 있고, 무거운 전제 인프라를 강요하지 않는다.
- **빠르게** — 벌크·벡터화·병렬. 작다고 느리지 않다.
- **정확하게** — 멱등·재개·검증이 기본값. 끊겨도 중복·누락 없음.
- **누구나 쉽게** — 선언형(YAML+가끔 SQL). 분석가도 바로 쓴다. DAG 코드 없음.

이 문서의 각 항목은 "현업 문제 → 왜 아픈가 → 접근 포인트 → 제품화 우선순위" 순으로 정리한다. 우선순위는 P0(MVP 핵심) / P1(확장) / P2(고급·대규모) 3단계.

---

## 무기 체계 한눈에

| 무기 | 성격 | 담당 영역 | 비고 |
|---|---|---|---|
| **Pugio** | 단검, 늘 휴대 | 수집·전송 (ETL 엔진) | 진행 중. 출발점 |
| **Gladius** | 군단병 주력검 | 변환·쿼리 (핵심 처리) | 일상 주력기 |
| **Spatha** | 기병용 장검 | 오케스트레이션 (의존성·스케줄링) | 여러 파이프라인 조율 |
| **Hasta** | 창, 지속 처리 | 스트리밍·CDC (지속 수집) | 끊김 없는 흐름 |
| **Pilum** | 투창, 일회성 | 디스패치·역방향 (reverse ETL) | 한 방향 발사 |
| **Scorpio** | 소형 노포, 정밀 | 관측성 (모니터링·lineage) | 정밀 조준 |
| **Ballista** | 대형 노포, 직사 | 대규모 분산 처리 | 단일 노드 초과 |
| **Onager** | 투석기, 곡사 | 백필·대규모 재처리 | 한 번에 크게 |
| **Scutum** | 방패, 방어축 | 데이터 품질·검증·보호 | 전체를 감싸는 계층 |

공격 계열은 무게·사거리 순으로 늘어선다(Pugio→Gladius→Spatha→Hasta→Pilum→Scorpio→Ballista→Onager). Scutum만 그 전체를 방어로 감싼다.

## Pugio — 수집·전송 (ETL 엔진)

> 단검. 가장 작고 늘 휴대하는 일상 도구. 이미 진행 중인 핵심.

### 문제 1. 인증 만료가 "에러"로 처리된다
- **왜 아픈가**: OAuth 토큰 만료·SSH 재연결이 파이프라인 실패로 잡혀 한밤중에 알림이 울린다. 실제로는 갱신만 하면 되는데 사람이 깨서 재실행한다.
- **접근 포인트**: 만료를 에러가 아니라 "갱신 트리거"로 분류. Auth Refresh Hook이 자동 갱신 후 그 지점부터 재개. 재시도 가능/불가 예외를 명확히 구분.
- **우선순위**: P0

### 문제 2. 끊기면 처음부터 다시
- **왜 아픈가**: 네트워크·프로세스 중단 시 어디까지 받았는지 모르고 전량 재수집. 시간·비용·소스 API rate limit 다 낭비.
- **접근 포인트**: Unit of Work에 결정적 ID 부여, 상태를 메모리가 아닌 영속 저장소(SQLite)에 기록. 재기동 시 미완료만 회수해 마지막 지점부터 재개. 재개 비용 ≤ 진행 중이던 청크 1개.
- **우선순위**: P0

### 문제 3. 페이지네이션·인코딩·rate limit의 잡일
- **왜 아픈가**: 소스마다 페이지네이션 방식(offset/cursor/page)이 다르고, euc-kr 같은 인코딩, 제각각인 속도 제한을 매번 손으로 처리. 본질 아닌 데 시간이 녹는다.
- **접근 포인트**: 선언형 필드로 흡수. `pagination.mode`, `encoding`, 토큰 버킷 기반 rate limit을 엔진이 처리. 사용자는 "무엇을/어떤 방식으로"만 선언.
- **우선순위**: P0

### 문제 4. 스키마 드리프트
- **왜 아픈가**: 소스가 컬럼을 추가·삭제·타입 변경하면 조용히 깨지거나 잘못된 데이터가 흘러든다.
- **접근 포인트**: 수집 시 스키마 스냅샷 비교, 드리프트 감지 시 정책 선택(통과·경고·차단). 깊은 검증은 Scutum과 연계.
- **우선순위**: P1

## Gladius — 변환·쿼리 (핵심 처리)

> 주력검. 가장 자주 쓴다. Pugio가 옮긴 데이터를 실제로 가공.

### 문제 1. 변환 로직이 코드여야만 한다
- **왜 아픈가**: 간단한 필터·리네임·캐스팅에도 DAG 코드나 스크립트가 필요. 분석가가 엔지니어에게 매번 요청 → 병목.
- **접근 포인트**: 직관성 계단. map(필드 매핑표) → steps(레시피 체인) → SQL → Python. 위 두 단계로 변환의 90%를 분석가가 직접. 엔진이 전부 SQL로 컴파일해 실행.
- **우선순위**: P0

### 문제 2. 변환이 느리다
- **왜 아픈가**: 행 단위 처리로 대용량에서 느려진다. 별도 분산 엔진을 띄우자니 무겁다.
- **접근 포인트**: 벡터화 엔진(DuckDB 등)으로 컬럼 배치·SIMD 처리. 단일 노드에서 수백 GB까지 편안. 새 실행 엔진을 만들지 않고 "쉬운 문법 → SQL 트랜스파일러"만 만든다.
- **우선순위**: P0

### 문제 3. 탈출구가 없다
- **왜 아픈가**: 선언형으로 표현 안 되는 복잡 로직에서 막히면 도구를 버리게 된다.
- **접근 포인트**: SQL(탈출구 1)·Python(탈출구 2)을 자연스러운 하강 경로로 제공. 쉬운 층은 위에, 강력한 층은 탈출구로.
- **우선순위**: P1

---

## Spatha — 오케스트레이션 (의존성·스케줄링)

> 기병용 장검. 사거리가 길다 = 여러 파이프라인을 가로질러 조율.

### 문제 1. 파이프라인 간 의존성을 손으로 챙긴다
- **왜 아픈가**: A가 끝나야 B가 도는데, 타이밍을 cron으로 어림잡다 보면 A 지연 시 B가 빈 데이터를 처리한다.
- **접근 포인트**: 선언형 의존성(DAG)을 데이터 준비 신호 기반으로 트리거. 시간이 아니라 "상류가 끝났는가"로 출발.
- **우선순위**: P1

### 문제 2. 재실행이 위험하다
- **왜 아픈가**: 실패한 잡을 다시 돌리면 중복 적재되거나 부분 처리가 꼬인다. 그래서 재실행을 무서워한다.
- **접근 포인트**: 멱등 재실행을 기본값으로. 같은 입력 → 같은 결과. 재실행은 예외가 아니라 정상 동작.
- **우선순위**: P0 (Pugio 코어와 공유)

### 문제 3. 유지보수 작업과 적재가 충돌한다 (lock 경합)
- **왜 아픈가**: compaction·VACUUM 같은 유지보수가 적재와 동시에 lock을 두고 경합. 멀티 리전·실시간 DML이 겹치면 단순 시간대 분산만으로 한계.
- **접근 포인트**: 우선순위 큐 + 실행 윈도우 선언. 적재(고우선)와 유지보수(저우선)를 구분, 겹치면 후자를 이월. "주말 오전" 같은 저부하 윈도우 타게팅을 선언형 필드로. lock 충돌은 재시도 가능 예외로 분류(Scutum과 연계).
- **우선순위**: P1

---

## Hasta — 스트리밍·CDC (지속 수집)

> 창. 들고 유지하며 찌르는 장병기 = 끊김 없는 흐름.

### 문제 1. 배치로는 신선도가 부족하다
- **왜 아픈가**: 일·시간 단위 배치로는 실시간성이 필요한 케이스를 못 따라간다. 그렇다고 Kafka/Flink는 운영 부담이 크다.
- **접근 포인트**: 폴링 마이크로배치로 가벼운 스트리밍부터. 고처리량 저지연이 정말 필요한 구간만 Ballista로 확장하되 사용자 선언은 불변.
- **우선순위**: P2

### 문제 2. CDC가 복잡하다
- **왜 아픈가**: 변경 데이터 캡처는 소스별 방식(로그·타임스탬프·트리거)이 제각각이고 누락·순서 문제가 생긴다.
- **접근 포인트**: cursor 모드에 cdc를 1급 시민으로. 결정적 ID로 순서·중복을 흡수. 소량 증분은 벌크 강제 없이 직접 경로로(과처리 방지).
- **우선순위**: P2

---

## Pilum — 디스패치·역방향 (reverse ETL)

> 투창. 던지고 끝 = 한 방향 발사.

### 문제 1. 가공된 데이터를 다시 외부로 보내기 어렵다
- **왜 아픈가**: 웨어하우스의 결과를 SaaS·CRM·알림 채널로 되돌려보내는 reverse ETL이 별도 도구·별도 설정. 통합이 안 된다.
- **접근 포인트**: sink를 외부 끝점(API·SaaS·webhook)으로 일반화. 같은 커넥터 계약으로 발사. 한 방향 디스패치라 멱등 키로 중복 발사만 막으면 됨.
- **우선순위**: P2

### 문제 2. 이벤트성 발사의 신뢰성
- **왜 아픈가**: 알림·webhook이 실패하면 조용히 누락된다.
- **접근 포인트**: 재시도 + DLQ를 디스패치에도 적용. N회 실패 시 격리 후 재투입.
- **우선순위**: P2

---

## Scorpio — 관측성 (모니터링·lineage)

> 소형 노포. 정밀 사격 = 어디서 무엇이 잘못됐는지 조준.

### 문제 1. 어디서 깨졌는지 모른다
- **왜 아픈가**: 파이프라인이 길어질수록 장애 원인 추적이 어렵다. 다운스트림이 이상한데 어느 상류 탓인지 모른다.
- **접근 포인트**: lineage 추적(어디서 와서 어디로 갔나)을 메타데이터로 자동 기록. 문제 지점을 역추적 가능하게.
- **우선순위**: P1

### 문제 2. 신선도·지연을 모른다
- **왜 아픈가**: 데이터가 늦었는지, 멈췄는지 사후에야 안다. SLA 위반을 사용자가 먼저 발견한다.
- **접근 포인트**: freshness·지연·처리량을 메트릭으로 노출. 임계 초과 시 알림. "마지막 성공이 언제인가"를 1급 지표로.
- **우선순위**: P1

### 문제 3. 비용이 보이지 않는다
- **왜 아픈가**: 어떤 파이프라인이 비용을 잡아먹는지 불투명. 최적화 우선순위를 못 정한다.
- **접근 포인트**: 단위 작업별 처리량·자원·(가능하면)비용을 기록. 무거운 작업을 가시화.
- **우선순위**: P2

---

## Ballista — 대규모 분산 처리

> 대형 노포. 무겁고 강력한 직사 = 단일 노드를 넘는 처리.

### 문제 1. 단일 노드 한계
- **왜 아픈가**: TB급·고처리량에서 단일 노드 벡터화로는 부족. 그렇다고 처음부터 분산을 깔면 무겁고 어렵다.
- **접근 포인트**: Executor 인터페이스로 백엔드 교체(로컬 → Spark/Flink). 사용자 선언(YAML)은 불변, 백엔드만 갈아끼운다. 점진 확장.
- **우선순위**: P2

### 문제 2. 정직한 한계선
- **왜 아픈가**: "인프라 없이 TB·실시간이 공짜"라는 거짓 약속이 신뢰를 깬다.
- **접근 포인트**: 처리 범위를 정직하게 문서화. 프레임워크가 주는 건 "용량·모드가 바뀌어도 사용자 경험과 신뢰성은 불변"이지 "모든 규모 무료"가 아님.
- **우선순위**: P1 (문서·설계 원칙)

---

## Onager — 백필·대규모 재처리

> 투석기. 곡사 광역 타격 = 과거 전체를 다시 친다.

### 문제 1. 백필이 무섭고 느리다
- **왜 아픈가**: 로직 변경·버그 수정 후 과거 데이터를 다시 처리해야 하는데, 운영 파이프라인과 충돌하고 시간이 오래 걸린다.
- **접근 포인트**: 백필을 별도 우선순위·별도 윈도우로 격리(Spatha 연계). 결정적 ID 덕에 안전하게 덮어쓰기(멱등). 범위 지정 재처리.
- **우선순위**: P1

### 문제 2. Small File / 파편화 (LinkedIn 사례)
- **왜 아픈가**: MERGE가 누적되며 테이블·객체 스토리지에 작은 파일이 수천 개 쌓인다. 읽기 성능 저하, 메타데이터 부하. 수동 OPTIMIZE/VACUUM은 유지가 어렵다.
- **접근 포인트**: (a) sink 쓰기 단계에서 청크 병합 — target file size 하한(예: 128MB 미만이면 묶기)으로 애초에 작은 파일을 덜 만든다. (b) 후보 테이블 자동 선정(파일 수·avg 파일 크기 기준) → 저부하 윈도우에 compaction. (c) dry_run·max table size·timeout 같은 안전장치. (d) 실행 로그 기록. 명령어보다 "어떤 기준으로 운영하나"가 핵심.
- **우선순위**: P1

### 문제 3. 스키마 마이그레이션
- **왜 아픈가**: 컬럼 타입·구조 변경 시 기존 데이터 전체를 재작성해야 한다.
- **접근 포인트**: 마이그레이션을 백필의 한 형태로 취급. 버전 관리된 변환으로 재현 가능하게.
- **우선순위**: P2

## Scutum — 데이터 품질·검증·보호

> 방패. 유일한 방어 무기 = 나머지 전체를 감싸는 계층.

### 문제 1. 나쁜 데이터가 조용히 흘러든다
- **왜 아픈가**: null·중복·이상치·타입 오류가 검증 없이 다운스트림까지 전파. 발견 시점엔 이미 의사결정에 쓰인 뒤.
- **접근 포인트**: 적재 직전 검증 게이트. 스키마·null·범위·중복 규칙을 선언형으로. 위반 시 정책(차단·격리·경고). DLQ로 격리 후 재투입.
- **우선순위**: P0 (멱등 가드는 코어)

### 문제 2. 데이터 계약이 없다
- **왜 아픈가**: 생산자와 소비자 간 스키마 약속이 암묵적. 생산자가 바꾸면 소비자가 깨진다.
- **접근 포인트**: data contract를 선언으로 명문화. 위반을 배포 전·수집 시 차단.
- **우선순위**: P1

### 문제 3. 멱등성 보증이 끝점마다 다르다
- **왜 아픈가**: 단일한 멱등 전략으로는 객체 스토리지·트랜잭션 DB·BigQuery를 다 못 덮는다.
- **접근 포인트**: 끝점 능력별 멱등 전략을 명시. 트랜잭션 MERGE 지원(PG·Snowflake) → temp→MERGE. MERGE 약함(BigQuery) → load to temp partition → atomic swap. upsert 없음(S3·객체) → 결정적 파일명(hash(unit_id))으로 덮어쓰기. 같은 unit은 같은 파일명 → 재실행해도 중복 없음.
- **우선순위**: P0

### 문제 4. 동시성 충돌 보호 (lock 경합)
- **왜 아픈가**: 적재·유지보수·외부 작업이 같은 자원에 동시 접근하면 lock 경합·데드락.
- **접근 포인트**: lock 충돌을 "재시도 가능 예외"로 분류해 retry/backoff로 흡수. 스케줄 분리는 Spatha, 충돌 흡수는 Scutum. 둘이 협업.
- **우선순위**: P1

## 통합 로드맵 (우선순위별)

### P0 — MVP 핵심 (가볍게·정확하게·쉽게의 바닥)
이게 없으면 "끊김·중복에 견디는 신뢰성"이라는 약속 자체가 성립 안 함.

- Pugio: 인증 자동 갱신, 재개, 페이지네이션·인코딩·rate limit 흡수
- Gladius: 선언형 변환(map/steps), 벡터화 실행
- Spatha: 멱등 재실행 (Pugio 코어와 공유)
- Scutum: 멱등 가드, 끝점별 멱등 전략, 기본 검증 게이트

### P1 — 확장 (운영을 실전으로)
단일 노드·중간 규모에서 실제 운영할 때 부딪히는 것들.

- Pugio: 스키마 드리프트 감지
- Gladius: SQL·Python 탈출구
- Spatha: 의존성 DAG, 우선순위 큐·실행 윈도우(lock 경합)
- Scorpio: lineage, freshness·지연 메트릭, 알림
- Onager: 백필 격리, Small File compaction
- Scutum: data contract, 동시성 충돌 흡수
- Ballista: 정직한 한계선 문서화

### P2 — 고급·대규모 (규모·실시간 확장)
처리량·실시간·외부 연동이 본격적으로 필요해질 때.

- Hasta: 스트리밍 마이크로배치, CDC
- Pilum: reverse ETL, 이벤트 디스패치
- Scorpio: 비용 추적
- Ballista: Executor 분산 백엔드 교체
- Onager: 스키마 마이그레이션

## 설계 원칙 (전 무기 공통)

1. **엔진은 빌린다, 만들지 않는다.** 벡터화·분산은 교체 가능한 백엔드 플러그인.
2. **재실행은 기본값, 예외가 아니다.** 모든 처리 단위는 결정적 ID로 멱등하게.
3. **사용자가 보는 것은 선언뿐.** 수집 루프·재시도·체크포인트·재개는 엔진이 흡수.
4. **상태는 절대 메모리에만 두지 않는다.** 죽어도 살아남는 것이 신뢰성의 근거.
5. **쉬운 층을 위에, 강력한 층을 탈출구로.** 선언 → SQL → 코드로 자연스럽게 하강.
6. **코어는 작게, 가속·확장은 선택적으로.** 작게 시작하는 것이 코어의 불변 약속. 벤더 가속·분산은 사용자가 선택적으로 지불하는 무게.
7. **각 도구는 독립하되 느슨하게 연결된다.** 따로 써도 제값, 같이 쓰면 시너지. 작은 표준 인터페이스로 맞물리고, 어느 것도 빼거나 갈아끼울 수 있다 — 락인 없음.
