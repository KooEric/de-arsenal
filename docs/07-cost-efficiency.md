# 07. 저비용 고효율 설계 (Cost & Efficiency)

> "저비용"은 할인 정책이 아니라 **아키텍처의 구조적 결과**여야 한다. 이 문서는 어떤 구조가 어떤 비용을 제거하는지, 무엇을 측정해 증명하는지, 그리고 우리가 **줄여주지 못하는 비용**은 무엇인지를 명문화한다.

## 비용 철학

1. **비용은 구조에서 나온다.** 서버리스 마진·클러스터 유휴·복사본 난립·재작업 — 큰 플랫폼 비용의 대부분은 기능이 아니라 구조에서 발생한다. 우리는 구조 자체를 바꾼다.
2. **가장 싼 연산은 하지 않은 연산이다.** 재개(재수집 생략), 증분(재계산 생략), 멱등(중복 제거 작업 생략), zero-copy(직렬화 생략) — 전부 "안 하기"의 기술이다.
3. **비용은 측정으로 증명한다.** "가볍다"는 주장은 벤치마크와 단위 지표가 뒷받침한다. 측정 없는 저비용 주장은 하지 않는다.
4. **정직한 비용 고지.** 우리가 못 줄이는 비용(대규모 분산, 진짜 실시간)은 숨기지 않고 문서화한다 (Ballista 정직한 한계선과 동일 원칙).

## 구조적 비용 우위 — 4개 축

### 1. 컴퓨트: in-process, 마진 없음

| | Databricks 계열 | Arsenal |
|---|---|---|
| 실행 형태 | 클러스터/서버리스 (기동·유휴 비용) | 프로세스 하나 (`pugio run` = 프로세스 수명만큼만) |
| 과금 구조 | DBU 마진 + 클라우드 인프라 이중 | 사용자 인프라 직접 — 중간 마진 0 |
| 최소 비용 | 최소 클러스터/웜풀 하한 존재 | 노트북에서도 0원 시작 |
| 엔진 | 관리형 Spark | 빌린 엔진(DuckDB) in-process — 오케스트레이션 오버헤드 없음 |

10GB 변환에 분산 클러스터는 낭비다. 단일 노드 벡터화가 커버하는 구간(수백 GB)에서는 구조적으로 이길 수밖에 없는 게임을 한다. 그 구간을 벗어나면 Ballista로 — 그때부터는 사용자가 선택적으로 지불한다(설계 원칙 6).

### 2. 스토리지: 오픈 포맷 단일 복사본

- 모든 도구가 **같은 Parquet 파일**을 읽는다 (Arrow/Parquet 허브). 수집본→변환용 복사→서빙용 복사 같은 도구 간 복사본이 없다. Databricks가 LTAP에서 "단일 스토리지 복사본"으로 도달하려는 지점에 우리는 구조상 처음부터 있다.
- 벤더 포맷이 아니므로 **반출 비용(락인 해소 비용)이 0**이다. 떠나는 데 돈이 안 드는 제품은 남을 이유를 가격이 아니라 품질로 증명해야 한다 — 그게 우리 포지션이다.
- Small file compaction(Onager, P1)이 스캔 비용·메타데이터 부하를 상시 억제한다.

### 3. 재작업: 신뢰성 = 비용 절감

신뢰성 기능은 전부 비용 기능이기도 하다. 명시적으로 매핑한다:

| 메커니즘 | 절감하는 비용 |
|---|---|
| 재개 (StateStore) | 중단 시 전량 재수집 — API 호출 요금, egress, rate limit 소진, 시간 |
| 결정적 파일명/MERGE 멱등 | 중복 적재 → 중복 제거 배치, 스토리지 낭비, 오염 복구 인건비 |
| rate limit 흡수 (토큰 버킷, 429 적응) | 소스 API 차단·과금 벌금, 재시도 폭풍 |
| 인증 자동 갱신 | 새벽 장애 대응 인건비 (가장 비싼 자원 = 사람의 수면) |
| 검증 게이트 + DLQ | 오염 데이터가 의사결정에 쓰인 뒤의 복구 비용 (가장 비싼 데이터 비용) |
| 증분 변환 (P1) | 매 실행 전체 재계산 — 컴퓨트의 대부분 |
| Arrow zero-copy | 직렬화/역직렬화 CPU·메모리 |
| compaction (P1) | 파일 수 폭증으로 인한 스캔·리스팅 비용 |

### 4. 인력: 선언형 = 병목 제거

- 분석가가 변환의 90%를 직접 (map/steps) → 엔지니어 대기열이라는 숨은 비용 제거.
- DAG 코드·인프라 운영 지식 불요 → 온보딩 비용, 전담 플랫폼 팀 비용 절감.
- `gladius compile`의 투명성 → 디버깅 시간 절감 (마법이 없으면 미스터리 장애도 없다).

## 증분 처리 전략 (P1 — 저비용의 핵심 확장)

전체 재계산은 저비용 제품에서 가장 큰 낭비다. Gladius의 증분 변환은 입력 파일
시그니처와 변환 스펙 해시를 SQLite에 기록해 신규분만 안전하게 처리한다:

```yaml
# transform.yaml (P1)
name: clean-issues
input: ./data/issues
incremental:
  mode: by_unit          # Pugio가 남긴 unit 단위로 신규분만 변환
  # mode: by_key         # 키 컬럼 기준 MERGE (upsert 소스)
steps: [...]
output: ./data/issues_clean
```

- `by_unit`: 입력 디렉터리의 unit 파일 중 **이전 실행 이후 추가된 것만** 변환해 append. Pugio의 결정적 파일명 덕에 "무엇이 새 것인가"가 공짜로 판별된다 — 수집의 멱등 설계가 변환의 증분 처리를 가능하게 하는 시너지.
- `by_key`: 신규 변환 결과를 기존 출력과 합치고 지정한 키의 신규 행이 기존 행을 덮어쓴다. 소스에서 삭제된 행은 추론하지 않는다.
- 변환 로직 변경 시(스펙 해시 변경 감지) 전체 재계산으로 자동 폴백한다. 부분적으로 낡은 결과를 조용히 내놓지 않는다(정확하게 > 싸게).

## 비용 가시성 로드맵

"측정 없는 저비용 주장은 하지 않는다"의 실행 계획:

| 시기 | 측정 | 구현 |
|---|---|---|
| P0 (M1~) | unit별 행 수·바이트·소요 시간·시도 횟수를 StateStore에 기록 | units 테이블에 `row_count`, `byte_count`, `duration_ms` 컬럼 — 지금 넣는다. 나중에 소급 불가능한 데이터 |
| P0 (M3) | 변환 벤치마크 수치를 저장소에 커밋 | `benchmarks/` — 회귀 감지 |
| P1 | lineage 자동 기록 + freshness·처리량 메트릭 + `pugio status --cost`: 파이프라인별 source→sink edge, 완료 unit의 누적 행/바이트/시간과 마지막 완료 시각 | Scorpio |
| P2 | 시간·바이트에 단가를 곱한 비용 환산, 무거운 파이프라인 랭킹 | Scorpio 비용 추적 |

## 효율 목표치 (측정 가능한 약속)

| 항목 | 목표 | 검증 |
|---|---|---|
| 재개 오버헤드 | 중단 후 재실행 시 재fetch ≤ 진행 중이던 unit 1개 | M1 E2E 테스트 |
| 완주 후 재실행 | fetch ≤ 1회 (경계 확인), 쓰기 0 | M1 E2E 테스트 |
| 유휴 비용 | 0 (상주 프로세스 없음 — 구조적 보장) | 아키텍처 |
| 도구 간 데이터 복사 | 0 (같은 Parquet을 읽음) | 아키텍처 |
| 1GB Parquet 변환 | 단일 노드에서 수십 초 내 (M3에서 실측치로 대체) | 벤치마크 |
| 설치→첫 수집 | 10분 이내, 전제 인프라 0개 | M4 문서 검증 |

## 우리가 줄여주지 못하는 비용 (정직한 한계선)

- **TB급·고동시성 분산 처리** — 단일 노드 벡터화의 한계 밖. Ballista(P2)로 확장하되, 그 인프라 비용은 사용자가 선택적으로 지불한다. "모든 규모 무료"는 거짓 약속이다.
- **밀리초 실시간 스트리밍** — Hasta는 폴링 마이크로배치(초~분)부터. Zerobus급 sub-second는 P2 이후에도 전용 인프라 없이는 불가함을 문서화한다.
- **소스 API 자체의 과금** — 줄여주는 것은 낭비되는 호출(재수집·재시도 폭풍)이지 정당한 호출이 아니다.
- **운영하는 사람의 존재** — 관리형 서비스가 아니다. cron·서버는 사용자 몫 (그 대가로 마진 없는 비용 구조를 얻는다).

처리 규모·지원 범위·sink별 멱등 보장의 구체적인 표는 [08-limits.md](08-limits.md)에
모아뒀다.
